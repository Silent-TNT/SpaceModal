# SpaceModal 对话生成演示

公开入口：https://www.spacemodal.com/generator-studio/
本目录为正式网站的对话生成工作台源码，随 GitHub main 分支通过 GitHub Pages 发布。

本机大模型入口为 `http://127.0.0.1:8080/generator-studio/`。在项目根目录运行 `node scripts/spacemodal_browser_proxy/local-server.mjs` 可提供网页和同源解析服务；凭据从项目根目录的 `.env.local` / `.env` 读取，不进入浏览器。其他端口的纯静态预览不在云端代理允许来源内；需要大模型时请打开 8080 入口。8080 页面会将缓存的公开代理地址迁移到本机同源接口。

流程：自然语言整理条件 → 用户确认 → 浏览器 HGNN+CVA 预测 → 两层联合几何与交通搜索 → 质量及结构差异筛选 → 平面、三维、贴邻图和导出。

### 首个合格方案提前展示（progressive-layout-v1）

每种布局模式在候选通过几何、连通、房间清单与玄关楼梯关系的完整校验后，立即发送首个合格方案；无需等待该模式或全部模式计算结束。各模式完成时更新可比较方案，最终沿用原预算、评分与差异筛选。界面显示已提供的合格方案数量和后续计算进度，用户可查看图纸、切换视图及下载。当前布局仍被保留时，更新不重置图纸缩放、三维视角或空间选择。

停止、超时或后续计算失败均保留本次已展示结果；阶段结果即时缓存，刷新后可恢复。阶段结果的 `partial=true` 与搜索摘要标记表示后续比较尚未完成，不表示跳过方案质量校验。完整计算结束后替换为最终结果。停止时另记录 `stopped=true`。

验证：`node website/scripts/test-progressive-generation.cjs`，使用真实浏览器 Worker 检查提前展示、完整结果、停止保留、下载、刷新恢复和后续错误保留，并比较提前展示与非流式计算的最终几何、评分及诊断。另运行采光及玄关面积规则回归。


## 图纸优先工作台

默认同屏显示完整两层三维体块、上二层下一层的平面图及两层异构拓扑；三维默认保持整体，不展开楼层。支持旋转、缩放、仅一层和复位，以及三类图纸的独立放大与返回总览。平面和拓扑可滚轮缩放、拖动平移、双击复位；选择空间可按楼层和空间 ID 联动高亮三维、平面与拓扑。

三维使用 Three.js 0.172.0 / WebGL2，以深度缓冲处理体块遮挡，保留原有功能配色。鼠标拖动或单指触控旋转，滚轮或双指缩放；依赖随站点保存，不依赖外部 CDN。下载展示会内嵌 Three.js 与模型数据，可离线打开；设备需支持 WebGL2，否则显示提示，平面与拓扑仍可查看。切换方案时释放旧几何与材质资源。依赖许可证位于 `vendor/THREE-LICENSE.txt`。

拓扑根据当前方案实际存在的空间按楼层建节点，区分房间、交通空间和楼梯。布局以每层真实占用网格的质心为起点，静态避让文字；楼梯同一 ID 且投影重叠时上下对齐在层间。圆形房间、方形交通、菱形楼梯保持异构语义，公共功能节点与公共空间之间的真实规划通行关系加重。通行与贴邻重合时优先显示通行，隐藏通行后可恢复贴邻线；点选空间时同时突出相邻节点及跨层联系。点线表示几何贴邻，实线来自 `model.connections` 的规划通行，虚线仅连接同一楼梯 ID 且上下层投影重叠的节点。各类边可独立隐藏；规划连接和楼梯对应不表示真实门扇、踏步或完整建筑验收。

界面采用无卡片边框的暖白画布，桌面三维占约一半，平面与拓扑各占约四分之一。顶部只保留品牌、当前方案、图标视图切换与更多菜单；导航、连接设置、解析方式、面积依据及导出集中在菜单。三维与平面工具在鼠标进入或键盘聚焦图纸时出现，触屏始终显示。拓扑边类型与图例通过“显示”展开；选中空间时突出关联节点与边。底部色点可悬停查看功能名，选择空间后只显示楼层、名称和实际网格面积。

对话默认收成单行输入胶囊；聚焦输入框或从更多菜单选择“对话与设计过程”展开。点击画布、按 Escape 或收起按钮关闭；生成时保留简短状态与停止按钮。历史对话、交通摘要、搜索依据与指标均留在展开区。两层平面默认上下排列，单独放大时桌面并排；窄屏按顺序重排图纸。

## 当前规则：stair-terminal-v6

### 评价与使用边界

先验证功能完整、空间不重叠、面积/宽度、卧室短边至少 2.4 m 且比例不超过 1.8、两层楼梯对应、有效公共入口和受保护活动区，再比较综合质量。以上尺寸是 demo 设计参数，不是规范结论。

`organization.js` 给客厅保留 3.0×2.4 m、餐厅保留 2.1×2.1 m、多功能室保留 2.4×2.4 m 的活动矩形。每个区域在可容纳的位置中比较，进行两轮相互修正。公共通路用连续方形通行带计算，默认宽 1.2 m，不得覆盖活动矩形或穿过独立卧室；独立房间入口需有连续 0.9 m 的共享边界。入口路径从玄关入口侧出发，二层从独立到达走道出发，避免把整个大玄关当作零路程起点。

楼梯是垂直交通端点，不属于同层可穿越公共网络。每层只保留一个楼梯出入口；一层可以玄关直接进楼梯，但客厅、餐厅等必须有不经过楼梯的独立公共路径。二层分配房间前预留宽度等于通路宽度的独立到达走道（默认 1.2 m），楼梯只与该走道连接。所有活动区通路检查都排除楼梯网格；连通图按层分开计算，禁止利用共享楼梯 ID 产生同层或跨层捷径。旧结果不自动升级验收，界面提示重新生成。

这是可调整的活动范围与网格通路近似，尚未验证家具布置、门扇、楼梯踏步/方向、真实人行或完整建筑规范。体块贴邻、规划出入口和可验证的网格路径分别记录；不能互相冒充。厨房可服务相邻家政空间，卧室可服务其阳台，独立房间不作为连接其他功能的通道。

`meal-routing.js` 按同层规划开口检查餐厨联系：优先直接连接；允许经玄关、客厅、餐厅、走道或多功能室联系，禁止经楼梯、卧室、卫生间、家政、阳台及另一厨房中转。有合适的餐厅边界开口时，厨房优先接餐厅。间接路线按公共空间中的开口间曼哈顿距离和中转次数加软成本（3 + 0.7×估算米数 + 1.2×中转数），不设普遍必须贴邻的硬约束，也不按数据集频率强制配额。该权重为工程偏好，并非学习得到；距离不代表真实步行距离。无同层餐厅的厨房单独标记，不虚构跨层送餐路线。结果及导出记录 `kitchenDining` / `kitchen_dining`。

综合评价包含面积偏离、形状、外边界、关系、上下层卫生间对应、公共空间穿行及路程、独立走道和公共空间中的实际通行占用。取消走道占比优先于一切的排序；走道为零也要计算公共空间交通占用。

面积超出统计四分位区间的代价随偏离增大而增长；剩余公共空间按新增面积代价比较接收房间，并可在已有公共房间之间调整连续边界。调整保留原入口范围，重新检查形状、尺寸、活动区、有效通路及整体评分，最多六轮、每轮十二次比较；通过后才保留，记录在 `geometry.publicAdjustments`。统计区间仍是软偏好，不能保证每个房间最终都落在 P25/P75 内。

### 公共区域优先与必要走道

先尝试保留活动区的公共通路。受阻时比较房间边界调整，允许从仍满足面积、短边和比例的独立房间边缘划出一段走道；最多两轮，每轮比较十个优先边界候选。只有改善受阻功能的调整才被保留，并记录服务目标、来源房间、面积和原因。未利用空白不会直接改名为走道。

每层走道 P75 是软偏好和偏离记录，不再作为硬性拒绝上限；不能仅因超过统计分位数否决一个可用方案，也不能通过把走道改名为客厅改善指标。当前搜索是有限候选及局部比较，不保证全局最短走道或最优布局。

公共区优先保留矩形/L形。原方式失败后，可以尝试无孔洞的其他连通形状，但仍须通过宽度、活动区和通行检查；不得靠房间名称将复杂空白解释为合理交通。

### 玄关—楼梯与两层联合调整

自动搜索：

- `near` 入门近梯：玄关与楼梯共享边界。
- `hall` 侧向错位：玄关和楼梯在横向错开，保持非直接贴邻；公共连接由实际通路决定。
- `public` 前后分离：玄关与楼梯分离，比较客厅、餐厅及客餐厅串联等公共组织。

公共区可在楼梯周边其他可用叶区域落位，不再只能塞进楼梯同宽的纵向条带；二层多功能室也同时接受活动区与通路检查。入口目前位于图面下侧，朝向尚未开放。

生成中可局部调整分割边界，并试探邻近可用楼梯位置、玄关位置/距离和保持两层对应的整体镜像。每个调整重新生成并检查两层、活动区与通路，只有改善整体评价才保留。`geometry.globalAdjustments` 记录成功调整，诊断记录尝试次数。这是有界联合局部优化，仍使用原分割器作为候选来源，没有引入完整通用建筑求解器。

`anchorValidation` 区分实际相贴关系与连接方式；`chain` 从受保护通路的规划连接中提取，玄关与楼梯共享墙面不再等同于所有模式相同。

### 方案组合与可解释结果

默认总预算 2400，分配到三种关系，每种 800。预算控制基础假设数；局部活动区、边界修复和整体调整另有有界检查，诊断计数明确区分两者。

先选质量接近的方案（最优综合分的 1.35 倍加 15 以内），再保留不同玄关—楼梯关系、独立走道取舍和功能入口图，最多四个，不强行补足四个。相同房间关系的重复切分不算新的组织类型。某类生成失败或质量不够接近时，不用同名方案冒充。

“活动区与通路”开关叠加受保护活动范围和实际计算的通路。结果摘要展示独立走道、公共空间通行占用与平均路径；“方案差异与搜索依据”显示各类预算、通过数、失败阶段和补路原因。失败计数含局部检查，不能相加当作被淘汰的候选数。全类失败时也返回诊断，不只显示通用报错。

旧结果保持可查看，重新生成才应用新规则。JSON 包含 `organization`、`routing_evidence`、`corridor_budgets`、面积来源、当前条件、规则版本和搜索诊断。导出 HTML 保留平面/三维/贴邻图，原有 `project_accepted=null` 不变，不冒充项目完整验收。

### 2026-10-12：楼层功能选择（floor-program-v1）

新设计默认一层1间卧室，二层增加1间客厅及1间家政用房。`bedrooms`仍为两层卧室总数；`bedrooms0`为一层数量（0至总数），二层采用剩余数量。`living1`、`utility1`为二层客厅、家政用房开关（0或1）。一层客厅、餐厨、家政和二层多功能室保留。需求卡片与本地/远程需求解析均支持这些字段，旧版在线解析器拒绝新增条件时重试旧请求格式，并在页面解析明确的楼层功能要求。旧客户端连接新版代理仍可用。

`createRoomProgram(bedrooms,bathrooms,balconyCounts,floorOptions)`的第四参数可传上述字段；省略时保留旧的全二层卧室清单，以维持调用方和原训练模型参考样本兼容。自由分割支持两层卧室及二层新增功能，优先保护卧室外边界位置，为新增二层客厅预留完整活动主体。面积统计按实际楼层与类别读取；不改变训练集或模型权重。保存的旧方案按旧楼层设置恢复，页面提示可重新设置；新生成的楼层版本随结果及几何JSON导出。

验证：`node website/scripts/test-floor-program.cjs --unit-only`；代理 `node scripts/spacemodal_browser_proxy/scripts/test-floor-program.mjs`；真实生成 `--case=0 --budget=1200`（13.5×11.4m、seed123、侧向错位）、`--case=1 --mode=public --budget=4800`（10.8×10.8m）、`--case=2 --budget=240`（所有卧室一层，二层无卧室）；真实浏览器 `test-floor-program-browser.cjs`。新生成均检查满铺、连通、房间清单、楼梯、活动区、通行、餐厨及外边界潜力。六组旧缓存只重核体素、连通与楼梯，部分缓存早于后续采光/玄关约束，不能称为当前规则的六组完整复跑。

新增功能不等于全局资源协调已完成：富余面积仍可能扩大卫生间、家政或公共房间；紧凑方案可能需要更高搜索预算。10.8×10.8m的本次侧向错位1200、前后分离1200未找到；前后分离4800找到。此处不保证默认2400、三模式分配一定成功，不用降低既有检查补齐候选。

`python website/scripts/build-area-prior.py` 从相邻 GraphSpace 的 `data/processed_1` 读取已有人工功能分组，只使用本项目 `data/05_review_drafts/training_v1/manifest.json` 中 300 个训练 ID。验证集及独立评估集不参与；原始数据不修改。记录数据与划分 SHA-256。

面积按住宅/楼层、显式 `functional_group_id` 合并 300 mm XY 网格去重；未分组保留原标注实例，不推测相邻同类是否属于同一房间。跨层体块每层只计一份覆盖投影。

`area-prior.js` 按建筑范围面积分组、长宽比（1.4 区分紧凑/狭长）、同层同功能实例数量分组选择中位数及 P25/P75。条件组至少 20 个实例且覆盖 10 套住宅，否则依次放宽长宽比、数量、尺寸，最终回退总体。分组阈值是 demo 统计配置，不是规范。数量较多时缩放超出最小面积的目标，不放宽尺寸及通行约束。来源记录请求分组、实际分组、回退状态、实例与住宅样本数。

阳台可按层设置 0–4，-1表示采用标注实例数量中位数；当前一层 0、二层 2。数量直方图含零实例住宅，但尚未证明零实例等同于真实无阳台，未分组片段也可能影响数量。界面明确说明这一限制。统计关系是同层共享网格边界，不能解释为真实门。

取消客厅—阳台硬绑定和固定贴邻加分。阳台可独立落位或以可变宿主辅助分割，最终允许连接玄关、客厅、餐厅、多功能室或可达卧室，必须接外边界。多个连接对象之间参考真实贴邻计数，再比较共享边长度。底层 `createRoomProgram` 无参数仍默认 [1,1] 以兼容旧数值参考；网页显式解析用户或统计数量。

固定两层，每层 3 m，300 mm 模数，范围长宽 6–18 m，卧室和卫生间各 1–8 间。新设计默认一层1间卧室，其余在二层；二层客厅和家政用房默认设置且可关闭。厨房、一层家政和二层多功能室沿用基本清单，尚未开放所有功能增减、朝向或用户指定房间位置。

## 本地运行与解析

项目根目录运行 `node scripts/spacemodal_browser_proxy/local-server.mjs`，访问 `http://127.0.0.1:8080/generator-studio/`。同源 `/api/generator/parse` 由服务端读取根目录 `.env.local` 的密钥，网页不接收密钥。网页可使用明确标识的本地解析；连接失败不冒充已调用大模型。支持“不要阳台”“一层两个阳台，二层阳台0个”。线上代理及发布操作另见代理目录，本次布局修改不自动发布。

### 公共空间完整性与复核导出（public-shape-v1）

公共空间优先矩形和 L 形。活动与通行修复放宽形状时仍限制为最多两处凹角，拒绝孔洞和点接触，并要求玄关局部宽度至少 1.2 m；保留原有面积、房间宽度、楼梯端点、餐厨通路及受保护活动区检查。评分增加凹角数和外包矩形填充率代价，不按矩形分块数量直接判断空间好坏。

平面只描同一空间的外轮廓。三维每层每个空间使用一个网格，顶底面保留精确覆盖，侧面仅沿真实边界生成；不显示矩形拆分形成的内部棱线。原有多矩形 geometry_v1 导出保持兼容。

右上角“更多操作 → 导出复核文件”生成 spacemodal_review_v1 JSON，包含全部展示候选、当前方案编号、生成条件、网格、几何、通路和原始校验。shapeReports 区分矩形分块数与面连通区域数，并包含凹角、填充率、最小局部宽度。它不包含连接设置或对话内容。旧方案的轮廓显示会更新，生成规则需要重新生成才生效。

### 数据集楼梯联合先验（stair-joint-v1）

`build-stair-prior.py` 只读取既定 300 套训练数据，按显式功能组取得楼梯与最大一层玄关的联合观察，生成 `stair-prior.json`。普通默认模板筛选矩形、短边至少 2.4 m、长边不超过 4.8 m，共 242 条观察；这是默认模板范围，不是建筑规范，也不代表其余标注有误。记录训练数据摘要、源案例、原始成对尺寸、相对位置、边界和关系模式；与面积统计的摘要必须匹配。

自由分割按建筑面积与长宽比近邻采样成对尺寸和落位，楼梯尺寸不再受客餐厅宽度控制。玄关尺寸独立变化，联合位置需经过网格、余边和空间容量适配；保留内部玄关候选。采样关系是偏好，实际关系按最终共边与X投影重新判定，通行仍按真实规划连接检查。预算根据近邻关系分布分配，直接近梯保留至少 10% 探索份额，最终方案不强制按比例展示。

预留可以跨多个空白分割叶，避免玄关与楼梯被迫同宽；不得覆盖已分配房间。每层根据实际已预留面积计算剩余房间容量。上层独立到达走道仍先于卧室分配；房间分配后的边界整理可让相邻完整房间吸收公共空间残边，但必须保持功能连通，并重新通过全部尺寸、完整性、活动和通行检查，不将闲置地块任意改名为走道。整理依据记录在 `integrityAdjustments` 中。

复核文件的每个候选增加 staircase：实际尺寸、面积、位置、玄关锚点、最终关系及训练来源。旧方案保持可读，需要重新生成才应用新规则。内部玄关不再标为建筑底边上的室外入口。

验证：`node website/scripts/test-stair-joint.cjs --generated`、公共完整性/楼梯端点/餐厨通路回归、六组户型与种子矩阵及真实浏览器生成与导出。单次方案数量可以少于四个，不填充重复或不合格方案。

### 二层卧室先分配采光位置（bedroom-facade-v1）

自由分割在预留上下对齐楼梯和独立上层平台之后，先分配二层卧室（可与阳台成组），再安排卫生间、其余阳台和多功能厅。卧室优先选择建筑边界上的位置，多功能厅不再提前占据完整外墙条带。一层餐厨、楼梯尺寸与玄关关系规则不变。

`daylight.js` 对最终网格逐间检查连续边界：卧室直接接建筑矩形边界，或与本层接建筑边界的阳台相邻。卧室—阳台共边及外露边界均需至少1.2m连续长度；这个值是概念生成的暂定开窗位置余量，不是法规、真实窗宽或采光达标结论。碎片接触不能累加通过，不能穿过卫生间、另一间卧室或走道借光。当前只支持矩形边界模型，不把未标注空白自动当作室外或天井。

局部修复、边界移动、镜像及最终候选均继续通过此检查。南向偏好、卫生间位置和多功能厅面积没有新增硬限制。`daylightPolicy` 标识新生成结果；旧缓存会提示重新生成。普通几何导出与复核文件包含逐卧室 `daylight`，记录方向、连续面宽、阳台关系及 `windowVerified:false`，不代表真实日照或照度已验证。

有限预算搜索每100个候选向页面报告进度。页面三分钟超时按连续无进度计算，避免复杂户型正常搜索被旧总时限终止；停止按钮保持可用。

验证：`node website/scripts/test-daylight.cjs` 检查封闭卧室回归、直接外露、阳台关系、跨层与借光排除、连续长度；`node website/scripts/test-daylight-generation.cjs` 重新生成六组固定条件（每组2400候选预算）；`test-browser-generator.cjs --daylight-only` 检查实际 Worker、三视图、响应布局、导出及缓存恢复。


### 玄关扩张与分级采光（entry-cap-v1 / tiered-facade-v2）

玄关初始预留尺寸保持不变。最终面积上限为 min(max(4.86, 统计偏好上限或目标面积×1.5), max(4.86, 一层面积×12%))，单位㎡。4.86㎡保底容纳现有最大初始锚点；其余参数是可调整的工程限制，不是建筑规范或训练得到的硬阈值。余地条带与整块吸收均在写入前检查上限，最终房间验收再次检查；边界调整也不能绕过验收。面积报告记录 maxArea。以10.8×10.8 m、统计偏好上限15.09㎡为例，上限13.9968㎡，0.3 m网格实际可用面积须不超过该值。

卫生间、家政必须有至少0.6 m的自身连续外墙；客厅、餐厅、厨房、卧室、多功能室至少1.2 m，可通过有足够外墙与连续共享边界的同层阳台满足。不能借用其它房间采光，零散外墙长度不能相加充数。生成时优先分配两层卧室，失败后还会尝试预留客厅并优先分配其它主要房间，再分配服务房间；待分配房间只选择满足各自门槛的外边界角位，最终再次验收；服务房间门槛较低，不替代卧室原有采光要求。玄关和走道不要求采光。该检查仅证明开窗位置潜力，尚未验证窗洞、朝向、照度与日照。

每个采光报告包含 tier 和 minimumContinuousFrontage，导出沿用 daylight 字段，几何导出增加 entry_limits；旧结果提示重新生成，保存的通过标记不代表通过新规则。

### 2026-10-12：联合面积协调（joint-area-v1）

本地Worker新增 `joint-area-model.json` 与 `joint-area.js`，保留原CVA位置模型。新网络输入功能、楼层、边界和完整需求数量，不含样本真实面积；两轮房间—楼层—整栋消息传递输出面积比例和标注覆盖率。覆盖率不作为可建设面积，也不会把缺失标注补成客厅。

冻结与现有餐厨、楼梯和面积统计一致的 `processed_1` 数据来源以及300/74开发划分。3个训练和2个验证案例有断开的人工功能组，整例排除；实际训练297例、验证72例，94个独立案例未读取。规范目录的5例几何差异记入来源审计，不覆盖标注。训练脚本 `scripts/train_joint_area.py` 对照独立网络、联合网络和联合约束损失，120轮；联合约束模型选中第50轮。验证房间面积MAE 3.689㎡，独立训练统计4.647㎡；仅为既定需求清单的面积预测实验，不是住宅生成成功率。重复训练三种模型参数逐项完全一致。
